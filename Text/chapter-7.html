7 Building robust agents with evaluation and feedback

This chapter covers

  • Introducing agent evaluation and feedback
  • Implementing test-driven agent development
  • Employing grounding, critic, and evaluation agents
  • Using Phoenix for evaluation and feedback

Evaluation and feedback provide the discipline that makes agent robustness measurable and improvable. They do not produce robustness on their own; a poorly architected agent will fail in ways that no evaluation suite can fix. What evaluation and feedback give you is visibility into how the system actually behaves and a mechanism for iterating toward better behavior over time.

Agent evaluation takes many forms, from benchmark and red team testing to grounding checks and agents that evaluate other agents. Feedback systems developed for agents come from human reviewers, evaluator agents, test outputs, and self-assessment. Each one answers a different question about the agent and occupies a distinct role in the development lifecycle.

While implementing evaluation and feedback is generally a requirement in any production agent system, this shouldn’t be the only time you look at hardening your agent systems. You almost always want to roll in this final layer (the fifth layer in figure 3.7, evaluation and feedback), which we will explore in this chapter.

7.1 Introducing agent evaluation and feedback

In this section, we zoom out and map the different evaluations and feedback loops around an agent (tests, humans, automated evaluators). Agents rely on an internal evaluation and feedback mechanism that is activated in the Learn step of the sense-plan-act-learn process loop. In addition, we can provide external mechanisms that evaluate and provide feedback to the agent or to ourselves. Figure 7.1 highlights the various steps and systems that may be used for agent evaluation and feedback: red team and benchmark testing, ground or critic agent evaluators, and human evaluation.

Figure 7.1 The external agent evaluation and feedback systems for a single user-facing agent. In the figure, a generative agent may face evaluation from a critic for general output feedback or from a grounding agent for context-specific feedback and evaluation.

Each evaluation type can provide feedback through one of two paths. It may flow directly back to the agent through critic agents, grounding checks, or other in-loop evaluators that influence the agent’s next action. Or it may flow into an evaluation database that stores test results and human feedback for later analysis, regression detection, and training signal.

Evaluation itself takes three main forms, each suited to different kinds of correctness. Deterministic test cases handle structured outputs where correctness can be checked exactly (the agent returned the expected schema, called the right tool, produced output that matches a known good answer). LLM and agent evaluators handle fuzzier natural-­language judgments, where correctness is a matter of degree rather than a match (rubric scoring, classification, or comparing two outputs for relative quality). Human evaluators handle the cases the other two miss: edge cases, policy concerns, tone problems, and anything that requires real-world judgment.

From this database, we can attach a specialized feedback agent whose role is to constantly review evaluations and feedback. This agent can generate reports and dashboards or send alerts if some activity becomes critical. While not all systems require all forms of evaluation and feedback, you generally want to employ the following methods when appropriate:

  • Red team testing—This evaluates whether specific terms, phrases, or patterns will break your system. Any user-facing agent or agent system should undergo some form of red team testing.
  • Benchmark testing—Tests how well an agent solves or attains a known problem or goal. These comprehensive tests are intended to cover entire agent systems but can also be used to evaluate individual agents.
  • Human feedback—Any user-facing agent system should provide a way for users to give feedback through thumbs up/down ratings, comments, or both. Human feedback is the foundation for how real agent systems are evaluated and improved in production, not a supplementary input. Raw feedback is noisy, though, and needs to be handled before it can drive decisions. Statistical aggregation, outlier detection for coordinated or anomalous patterns, stratified sampling that weights expert versus casual users, and follow-up review on flagged outputs are the practical techniques for separating signal from noise.
  • Grounding agent—This agent applies grounding evaluation to RAG systems, checking whether a response is grounded in the context the knowledge agent retrieved. Grounding itself is a general technique for verifying that model output ties back to a verifiable source, and it applies beyond RAG to tool-call validation, memory verification, and citation auditing. The grounding agent is the implementation; grounding is the technique. Take the source, take the output, and check whether the output’s claims are supported by the source. Apply it wherever the agent has an authoritative source to defer to.
  • Evaluation/critic agent—This agent provides an additional level of evaluation and feedback for internal reasoning during planning, determining goal completion, and understanding action output. Although this type of agent can be added to any agent workflow, it is commonly used in the flow and collaboration multi-agent patterns.

You may encounter other evaluation and feedback patterns that derive from or extend these methods. Do not wait until the later stages of development to employ evaluation and feedback. Much as testing drives test-driven development (TDD), the same practices apply when building agents.

Governance for multi-agent systems

Multi-agent systems introduce a class of failure modes that single-agent systems do not have. The most concerning is agent collusion: a setup where multiple agents reinforce each other’s wrong answers because they share assumptions, biases, or training data, and no external check breaks the loop. A grounding agent that uses the same model as the agent it is grounding will tend to validate the same hallucinations the original agent produced.

Several practices reduce collusion risk. Use different models for evaluator agents than for the agents being evaluated, because models from different providers tend to fail in different directions and an evaluator with the same training data shares the same blind spots. Where different models are not practical, use different prompts and personas to push the evaluator toward a different stance (an evaluator prompted to find problems behaves differently than one prompted to confirm correctness, even on the same model). Periodically include human review on flagged outputs and on a random sample of unflagged outputs, because an automated evaluation system that is never checked against ground truth can drift undetected.

Governance beyond collusion includes a few standard moves worth naming. Define a clear authority hierarchy (which agent has the final say when evaluators disagree). Log every agent-to-agent message so disagreements and decisions are auditable after the fact. Set escalation rules for cases where evaluators cannot agree or where confidence drops below a threshold, with human review as the fallback. Limit each agent’s authority to what its role requires, so a single compromised or malfunctioning agent cannot cascade decisions across the system.

These practices are not unique to evaluation agents, but they show up most acutely there, because evaluation is where the system’s measure of its own correctness lives. An evaluation layer that colludes with the agents it is evaluating is worse than no evaluation layer, because it provides false confidence. Treating governance as part of the evaluation design, not as a separate concern bolted on later, is the durable framing.

7.2 Implementing test-driven agent development

Test-driven development is an established software engineering practice where tests are written to express requirements before the implementation that satisfies them. The honest version is that TDD is often more aspirational than universal: many teams write tests after an MVP, especially under deadline pressure, and the discipline is more useful as a habit than as a rule. What stays true is that defining what good looks like before building it produces cleaner systems than the alternative.

The same principle applies to agents. Defining what a good agent response looks like and then building the agent to satisfy that definition is more disciplined than building the agent and hoping the evaluation catches problems later. As shown in figure 7.2, this approach is known as test-driven agent development (TDAD).

Figure 7.2 The human process of developing agents using TDAD: first, we think of goals and benchmarks; then we test, develop the prompt, refactor, and repeat the process.

The agent version of “what good looks like” is usually expressed as rubrics rather than unit tests. Rubrics specify the criteria a response should meet (factual accuracy, grounding in retrieved context, appropriate tone, structural correctness), and the evaluation pipeline checks the agent’s output against those criteria. We will return to rubrics later in the chapter, where the connection between TDAD and rubric-based evaluation becomes concrete.

The figure demonstrates the human process of building an agent (prompt and tools) by following the TDAD process. This process starts with thinking, testing, prompting, and refactoring. In TDAD, we first establish a set of goals or input benchmarks against which the agent will be tested, identifying expected responses and known-bad responses for each.

Agent testing extends beyond input and output comparison. A complete test observes the agent holistically: which tools it selected, what reasoning steps it produced, whether it stayed grounded in retrieved context, how many steps it took to reach an answer, how much latency and cost the run accumulated, and how it behaved when something failed. Each of these is a testable property, and any of them can be wrong even when the final output looks right.

Examples of incorrect outputs and incorrect intermediate behavior help evaluation agents distinguish good runs from bad ones. The same agent that produced a correct answer through five wrong tool calls is not the same as one that produced it through two right ones, and a complete test will catch the difference.

Then we test, and at the start of testing we should expect the agent to fail. Because the LLMs that power agents are variable, run each test multiple times to confirm the failure is consistent rather than a one-off sample. From the failure, identify the minimum updates to the agent’s prompt and tools that will let the benchmark pass.

“Minimum” is worth defining because it is the part most practitioners get wrong. The progression that works in practice, from smallest to largest change, goes like this: change a single word for tone or precision, add a clause to an existing sentence, add a single sentence to an existing section, add a new section to the prompt, add or modify a tool, change the model or its parameters. Try the smaller changes first and only escalate when they do not fix the failure.

Doing the minimum keeps prompts lean, preserving model performance and reducing latency on every call. Bloated prompts emerge from teams that add a paragraph every time something goes wrong, never delete anything, and end up with multipage system prompts where each section contradicts another. The discipline is not just to make the smallest change, but to remove things that no longer earn their place.

Next, we retest and refactor. We rerun all previously passing benchmarks to confirm the agent is working as expected. When previously passing benchmarks break, we go back and refactor the prompt, making minimal changes to allow all benchmarks to pass. Continue refactoring and testing to confirm that the agent passes all benchmarks.

We will generally want the agent to pass all benchmarks before continuing. But it is not unusual for previous benchmarks to fail because of changes made to support other benchmarks. This will likely happen because one benchmark may contradict another. For example, one benchmark may force an agent to think step by step, while another may require it to answer quickly without thinking. In such cases, when benchmarks start to break down, you may want to consider the following questions and options:

  • Should all benchmarks pass? If the answer is no, use the failing benchmarks as an example of wrong output. Another reason the answer may be no is that you expect the agent to perform well on only 90% of your established tests. This may be because you have dozens or hundreds of benchmarks developed over time, and achieving a 100% pass rate is not always practical.
  • Does adding an agent make sense? If your agent is passing most benchmarks but failing on a subset, one option is to add a specialized agent that handles only those cases. This introduces a routing problem (which agent answers a given input), and the router itself can make mistakes that increase the overall error rate before specialization pays off. Routing accuracy is its own evaluation problem.
  • Should you refactor your entire agent? Adding agents is a lot more work, and often it makes more sense to break the agent down and rebuild it. Fortunately, rebuilding an agent often only involves recreating the agent’s instruction prompt from the beginning. This time, when you rebuild the agent, the instructions focus on the benchmarks that caused the most problems or are the most complex.

NOTE “Mixture of experts” inside an LLM refers to a layer that routes tokens to subnetworks within a single forward pass, which is not the same as multiple agents with separate calls. The multi-agent version is closer to specialist routing or ensemble. It’s worth keeping the terms distinct. Specialization increases complexity, evaluation overhead, and cost. Before going there, consider whether refactoring the single agent (better prompt, tools, grounding) closes the gap. Specialization is the right move when the failing subset is genuinely distinct, not when the single agent is one edit away from passing.

Generally, you will want to apply TDAD across an agent system and focus on the individual specialized agents where most of the work is done. Doing this requires agent and agent system benchmarks that can be applied and tested at different levels of granularity. But if you don’t, you risk gaps in functionality that might surface during production use.

7.2.1 Exploring TDAD in practice

Let’s go through the process of creating an agent with TDAD. This demonstrates the process so that you can use it yourself to build a single- or multi-agent system. Figure 7.3 presents a single-agent system and some initial benchmarks we would expect this agent to achieve. In this example, our benchmarks consist of a set of questions specific to some fictional source material.

Figure 7.3 Architecture of a simple RAG knowledge agent. The goal of the agent is to answer questions from a benchmark by searching its knowledge base and returning answers. A simple evaluator LLM evaluates the answer based on the expected and incorrect answers from the benchmark test. The accuracy of the RAG agent can be determined by the percentage of benchmark questions it answers correctly.

In the figure, the RAG agent relies on a simple retrieval architecture pattern. In this pattern, an agent receives a question about some external knowledge it has access to. From there, it breaks the question down into searchable words and phrases and then uses those terms to search its knowledge base. If knowledge is found, it uses that as context to answer the user’s question; otherwise, it says that nothing was found. This answer is then passed to an evaluator along with the expected and incorrect answer candidates paired with the benchmark. The evaluator then uses this information to determine whether the benchmark passed or failed.

7.2.2 Coding and testing the RAG agent

Now that we have an idea of the benchmarks, we should evaluate our agent as we build the minimum code to support them. At this point, our focus is to do enough that we can ask the agent a question. It will answer, and evaluate that answer. How you build this code is up to you, and you may want to use TDD for the regular software pieces, such as database connectivity and other tools.

Listing 7.1 shows the code that will run the agent through the benchmarks table. At this stage, the evaluation is simple and uses string matching against the expected answer. For the agent itself, all we have defined is the role/persona in the instructions and nothing else. Now that we have a fully working agent system that fails all benchmarks, we can begin refactoring and building the agent prompt instructions. We want to start by looking at easy fixes, such as correcting output formatting or providing instructions for handling data. That’s what this next piece of code does.

#2 Inform the agent to always answer with a single word.

What we did in the listing was ensure that we always output single-word answers, which match our benchmark formatting. Next, we provide some instructions for breaking down the question, but for now, we avoid specifically instructing tool use. As a guide, we want to avoid formatting and tool use instructions in the prompt.

Agent prompt design rule

Early agent development relied on prompts that explicitly listed every tool and dictated output format in detail. Modern practice registers tool metadata (names, descriptions, parameter schemas) through the SDK, and the model uses that metadata to choose tools without the prompt walking through each one. The shift is that prompts no longer need to repeat what the tool metadata already says.

Tool instructions have not disappeared, though. AGENT.md files, system-prompt sections, and inline guidance are still common when specific tools need specific handling (use this tool only for legal queries, and prefer the local tool over the remote one). The shift is in responsibility, not requirement.

Output format follows the same pattern. Structured output libraries let you declare the response shape (a Pydantic model, a JSON schema), and the SDK expands that declaration into the prompt and enforces validation. Dynamic discovery is convenience, not magic: the format still ends up in the prompt, just expanded by the SDK rather than written by hand.

Formatting and tool-use instructions should be provided outside the prompt. For formatting, this means setting the output type on the agent and then constructing the output you want from that strongly typed format. For tools, the tool description and the comment at the head of the function should provide the explanation the agent requires to use the tool.

Keeping formatting and tool details out of the instruction prompt makes it easier for the agent to adapt to new tools or output formats without rewriting prose. This is a clean separation, not a rule against long prompts. Long, specific system prompts are common in production, especially for agents that need to avoid certain behaviors, enforce policies, or operate in regulated domains; the system prompts shipped by major LLM providers themselves often run several thousand tokens.

Any time you change an agent’s instructions, the agent may behave differently. The risk varies with what you change: tightening a constraint usually has predictable effects, while adding a new section or modifying tone can interact with the rest of the prompt in ways that surface only under evaluation. The right move is not to avoid prompt changes but to evaluate the impact of each change against your benchmarks before treating the new prompt as the new baseline.

Run the refactored agent against the benchmark, and you will see roughly 40% accuracy, with two of five questions answered correctly. The trace output in listing 7.3 shows where the failures come from. The agent sends its first query directly to the retrieval tool, and when the retrieval returns weak or empty results, the agent accepts the absence as the answer rather than trying a different query.

The diagnostic is worth seeing clearly because it tells us exactly what to fix. The retrieval system is working (it returns results when the query is well formed), but the agent has no strategy for when those results do not contain the answer. What the agent needs is a query-refinement step: when retrieval returns nothing useful, rephrase the query and try again before concluding the information is absent.

The fix lives in the agent’s instructions, not in the retrieval system. Adding a clause that tells the agent to refine and retry queries when results are thin (try synonyms, broader terms, or a decomposition into subquestions) gives the agent the recovery behavior it was missing.

Run the code and you will see roughly 60% accuracy on the benchmark, with three of five questions counted as correct. Before reading this as agent failure, look at which questions the evaluator marked wrong and what the agent actually returned. Two of the failures in this run are not retrieval problems at all: the agent returns “Photons.” instead of “photons” and “Water currents” instead of “currents,” both of which are correct answers that fail the evaluator’s strict equality check.

This is a useful failure to encounter because it surfaces one of the most common evaluation bugs in agent development. Strict equality (expected == actual) on natural language output is almost always too brittle. Tightening or loosening punctuation, case, and trailing words is normal model behavior, and an evaluator that does not normalize for these will flag correct answers as wrong.

The fix lives in the evaluator, not in the agent. Changing the check to something like expected.lower() = actual.lower() accepts the agent’s outputs as correct and returns the benchmark to 5/5. For production benchmarks, normalization (lowercasing, stripping trailing punctuation, removing whitespace) is the minimum; LLM-as-judge evaluators handle the harder cases where multiple phrasings can be correct.

If your score is 100% after the evaluator fix, rerun the test to confirm consistency before concluding the agent is solid. From there, depending on the results, you can continue refactoring or call this round complete.

The benchmark evaluator in the last section was very simple and performed only word matching for validation. In the real world, though, we rarely expect an agent to return a single word, and the response is often far more complex. To handle more complex output, we will use an agent to evaluate and score the benchmark.

7.3 Employing grounding, critic, and evaluation agents

When evaluating an agent’s output, we have a few options and patterns, including grounding agents, critic agents, and evaluation agents. These three patterns help establish practices we can use to evaluate an agent’s output for a specific application or use case, such as knowledge RAG. Figure 7.4 compares the three patterns. It also shows the use cases they best apply to, and when to use them.

Figure 7.4 Three forms of agents for evaluating agent output: grounding, critic, and evaluation. The grounding agent is specific to evaluating RAG agent output. The critic agent is designed to critique generated content, and the evaluation agent is used for more complex output.

The grounding agent is specific to the RAG or retrieval agent and is used to make sure the output is grounded in the context the agent used to create the answer. A grounding agent may provide feedback and force the retrieval agent to regenerate the answer or block it entirely. This agent is essential when the answer needs to be grounded in the context of the source material.

Critics evaluate generated content and provide feedback when it does not meet the criteria or rubric. They block content that fails evaluation and require regeneration, with a retry ceiling to prevent infinite loops.

The retry ceiling is a real architectural decision, not a casual heuristic. What happens on the fourth attempt determines whether the system fails safely or becomes a hidden source of bad output. Common patterns include returning a static fallback response with an apology, escalating to a human reviewer for outputs above a certain stakes threshold, returning the best of the failed attempts with a confidence flag, or surfacing an explicit “could not produce acceptable output” error to the calling system.

The right choice depends on context. User-facing systems usually need graceful fallbacks (a generic but safe response is better than an error). Internal pipelines can fail loudly because the downstream system needs to know retries were exhausted. High-stakes work earns human escalation because returning anything automatically when the agent has failed three times in a row is the wrong move.

For more complex output that may combine retrieval and novel generation, we use rubrics to help align the content by providing evaluation as feedback during generation. Because determining the cause of failures in this process may be expensive, the feedback/evaluation is sometimes combined with the complex output. This allows users to understand and evaluate the output themselves and adjust accordingly.

7.3.1 Reviewing the grounding agent

As a review, grounding is the process of making sure an answer is supported by context and citations. The practice of grounding isn’t limited to RAG knowledge agents; the concept can also be applied to other patterns, such as agent critics. Figure 7.5 revisits the architecture of the RAG knowledge agent, now with a grounding guardrail agent. Adding a grounding agent requires the retrieved knowledge context to be passed to both the RAG agent and the guardrail agent. The RAG agent uses the context to generate an answer, and the grounding agent confirms that the answer is grounded in the context.

Figure 7.5 RAG knowledge agent coupled with a grounding agent. Both agents are given the same context. The RAG agent generates an answer from the context, and the grounding agent verifies that the answer is grounded by reviewing that same context.

After the answer routes through the grounding agent, a few options are possible. How best to handle grounding output will depend on your particular use case, and you could also combine options. For example, you might have a grounding agent reject an answer three times before blocking the output entirely and providing a static statement.

7.3.4 Understanding the role of rubrics in evaluation

The evaluation strategy depends on what the agent is producing. Agents that produce structured outputs against a known target (classification labels, extracted fields, optimization decisions) can be evaluated using traditional metrics such as accuracy, precision, recall, and F1 score. The right-or-wrong question has a clean answer in these cases, and the standard ML evaluation toolkit applies directly.

Agents that produce open-ended natural-language outputs (summaries, explanations, plans, creative content) require different methods. Accuracy is rarely well defined when multiple phrasings can be correct and quality is multidimensional, which is why rubrics, LLM-as-judge evaluators, and human review take over from numerical metrics. Most production agents are a mix of both kinds, with structured pieces evaluated numerically and natural-language pieces evaluated through rubrics or by judges.

Picking the right evaluation method for each piece of the agent’s output is part of the design work. Defaulting to rubrics when accuracy would suffice creates unnecessary evaluation complexity, and defaulting to accuracy when rubrics are needed yields brittle measures that miss what actually matters.

In education, a rubric defines structured criteria and standards a student must meet to receive a particular grade. The same idea applies to evaluating agent output, with one important addition: the rubric itself has to be validated against human judgment, or it scores consistently but consistently wrong. We can follow these steps to define a rubric to evaluate the output’s performance:

  1. Identify the purpose and objectives. Determine the goals you want the output to accomplish. For example, do you want to evaluate the quality of recommendations for a given audience or the overall quality for a given subject, format, or other input?
  2. Define criteria. Develop a set of criteria or dimensions that you will use to evaluate the output. These criteria should align with your objectives and provide clear guidelines for assessment. Each criterion should be specific and measurable. For example, you may want to measure a recommendation by how well it fits the genre, subject, and format.
  3. Create a scale. Establish a rating scale that describes the levels of performance for each criterion. Standard scales include numerical scales (e.g., 1–5) or descriptive scales (e.g., Excellent, Good, Fair, Poor).
  4. Provide descriptions. For each level on the scale, provide clear and concise descriptions that indicate what constitutes a strong performance and what represents a weaker performance for each criterion.
  5. Apply the rubric. When assessing a prompt or agent persona, use the rubric to evaluate the prompt’s performance against the established criteria. Assign scores or ratings for each criterion, based on the descriptions for each level.
  6. Calculate the total score. Depending on your rubric, you may calculate a total score by summing up the scores for each criterion or using a weighted average if some criteria are more important than others.
  7. Ensure evaluation consistency. If multiple evaluators are assessing the profile, ensure consistency in grading.
  8. Review, revise, and iterate. Periodically review and revise the rubric to ensure it aligns with your assessment goals and objectives. Adjust it as needed to improve its effectiveness.

Rubric evaluation is a concept that can be applied in a critique or evaluation of output. It defines how well a response aligns with a given rubric’s specific criteria and standards. You can also think of this as the baseline expectation for an output.

There are several other important considerations when using grounding with profile evaluation. The list below highlights some key considerations for each concept we have covered:

  • Rubrics—Rubric development and evaluation involve aligning responses with the criteria, objectives, and context defined by the rubric and output. This is a complicated process that may require additional iteration to refine the best rubric for your specific use case.
  • Evaluation—Evaluating involves assessing whether a response directly addresses the rubric criteria, stays on topic, and adheres to any provided instructions. There are many ways to evaluate LLMs, from having them act as a judge or evaluator to using deterministic code or a human.
  • Scoring—Evaluators and evaluations gauge accuracy, relevance, and adherence to standards when assessing rubrics. When building rubric evaluation systems, be sure to record and track scores for later analysis and improvement.
  • Logging—Logging captures every input, output, and intermediate step produced by the agent and its evaluators, creating a trail that can be reviewed, queried, and replayed later. Without logs, agent failures show up as user complaints with no way to reconstruct what happened. With logs, the same failure becomes a debuggable trace. Logging needs to cover the evaluator agents too, not just the agents producing the final response. An evaluator that incorrectly passes bad output or fails good output is a silent source of error that only logs can surface.

A well-evaluated response aligns with all the rubric criteria within the given context and objectives. Responses that fail miss the criteria, context, and goals entirely.

A critic agent is a specialized evaluator that scores output against the entire rubric (criteria plus scale). We can build on this example by building a critic agent that evaluates the image according to the style guidelines rubric. The critic agent rates how well it applies the styles. It then passes or fails the image based on these guidelines and the accepted rubric score.

Why rubrics matter

A pass/fail evaluation from an LLM judge gives very little insight into why an output passed or failed. The criteria in a rubric provide a detailed critique of what was good or bad, which is what lets us refine the bad while preserving the good. The choice of criteria determines what the rubric can see.

Useful criteria for agent output go beyond surface quality and into behavior: hallucination rate (are claims supported by sources), reasoning quality (do intermediate steps follow logically), tool usage correctness (right tool, right parameters, right interpretation), and error handling (does the agent recover from failures or compound them). These behavioral criteria pair with the surface criteria from earlier (accuracy, grounding, structural correctness, tone, completeness). The rubric is only as good as the criteria you include.

Before we look at the code, let’s go through the process of building a rubric again to evaluate a response output. There are eight steps to defining a rubric as applied to our image generation example:

  1. Identify the purpose and objectives. The purpose of our image-generating agent is to generate an image according to a strict set of guidelines.
  2. Define criteria. For simplicity, we will evaluate how a particular output image aligns with the following style guidelines and used previously to generate images: 
## Style Guidelines for All Images:
- **Consistency**: Each image should maintain the same photographic quality with 3D-rendered elements seamlessly integrated
- **Color Palette**: Use a consistent scheme of blues, purples, warm golds, and greens with pops of bright accent colors
- **Lighting**: Professional photography lighting with dramatic but warm tones
- **Infographics**: Semi-transparent holographic projections that don't overwhelm the main subjects
- **Characters**: AI robots should be cute, approachable, and distinctly different from each other while maintaining a family resemblance
- **Icons**: Use universally recognizable symbols (lightbulbs for ideas, gears for processing, hearts for alignment, etc.)
- **Mood**: Optimistic, educational, and slightly futuristic without being cold or intimidating
  1. Create a scale. Again, keeping things simple, we will use a simple scale of 1–5 (1 is poor and 5 is excellent).
  2. Provide descriptions. See the general descriptions for the rating scale shown next:
Score the image on a scale of 1 to 5 using the following scale:
1. **Poor**: The image does not meet the style guidelines at all.
2. **Fair**: The image meets some of the style guidelines but has significant issues.
3. **Good**: The image meets most of the style guidelines but has minor issues.
4. **Very Good**: The image meets all the style guidelines with only a few minor issues.
5. **Excellent**: The image meets all the style guidelines perfectly.
Pass the image if it scores 2 or higher, otherwise fail it.
  1. Apply the rubric. At this stage, with the rubric assigned, it is an excellent exercise to evaluate generated images against the rubric manually.
  2. Calculate the total score. For our rubric, we will take an overall score across all criteria. You could also score each element and use a combined or average score for evaluation.
  3. Ensure evaluation consistency. Asking the LLM to grade and then pass/fail provides more consistent results than just asking for a pass/fail.
  4. Review, revise, and iterate. We will review, compare, and iterate on our profiles, rubrics, and the evaluations themselves.

This basic rubric can now be applied to evaluate the responses for our image generator. We will create a critic agent that follows the rubric and grades the images. It will then pass or fail each image based on the criterion score, which is 2 out of 5 according to step 4 above.

Listing 7.12 adds the critic agent along with a vision tool (describe_image, not shown) and the means to evaluate the styles using our generated rubric. This agent and the image generation agent now run in a loop. The loop is controlled by whether the critic passes or fails the generated image’s style. The loop continues as long as the critic fails the output image.

According to our rubric defined previously, we require a score of 2 out of 5 or higher to pass. This is a low bar set deliberately for the demonstration: the critic passes most images easily and the loop runs to completion in reasonable time. Raising the threshold to 3 or 4 would cause the critic to fail most images and the loop could run indefinitely or hit its retry ceiling.

In production, this threshold is a critical design decision with real consequences. A threshold set too low ships output to users that fails quality standards. A threshold set too high causes most outputs to fail evaluation, which either burns retry budgets, escalates everything to humans, or starves the system of acceptable responses. The right threshold depends on the cost of a false positive (passing bad output) versus a false negative (failing acceptable output) for the specific application.

Calibrating the threshold is part of the rubric validation work covered earlier. Score a sample of outputs against the rubric, have humans label which ones should have passed and which should have failed, and set the threshold at the score where the agreement between rubric scores and human judgment is highest. Revalidate the threshold whenever the rubric, the agent, or the underlying model changes.

The same principles we used to build the critic agent here can be applied to other use cases where the output is generated and varies widely. Even with that variation, we can establish rubrics that allow critical agents to evaluate complex outputs such as images, reports, graphs, and other complicated examples.

Annotations let internal reviewers (developers, QA, domain experts) attach structured labels to specific spans or traces, marking things like “incorrect tool selection,” “good response,” “needs review,” or any custom label that fits your evaluation needs. These annotations get stored alongside the trace data and become queryable signals you can use later.

The payoff is that annotations turn ad hoc judgment into structured data. A developer noticing that the agent picked the wrong tool can flag the span, and later you can pull every span flagged with that label, compare them against the unflagged spans, and look for patterns (does it happen on long prompts, with specific tools, after certain types of user queries). Filtering the trace dashboard by annotation lets you cross-­reference quality labels against operational metrics like latency, cost, and token usage to see whether bad responses correlate with specific cost or performance patterns.

This is also how informal review becomes a dataset over time. Spans flagged “incorrect” across many sessions become a regression test set: rerun the agent against those inputs after a prompt change and see whether the new version handles them correctly. Without annotation, the same observations live in Slack threads and meeting notes and never become reusable evaluation material.

Incorporating the principles and patterns of evaluation and feedback into your agent development and production cycle not only improves the quality of those agents but also increases their robustness. As a golden rule, you should never promote agents into production systems unless you employ evaluation and feedback patterns.

Summary

  • Robust agents require evaluation and feedback baked in from the start. Tie the Learn step of sense-plan-act-learn to external evaluators, a feedback store, and (optionally) a monitoring/alerting feedback agent.
  • Use a mix of methods: red team testing for safety breaks, benchmark testing for goal attainment, human feedback (thumbs/comments) with verification to reduce bias, and automated evaluators (grounding/critic/evaluation agents) where appropriate.
  • Test-driven agent development (TDAD) flips the process: define benchmarks (including wrong examples), expect initial failures, and run each test multiple times for consistency. Then make the minimum prompt, tool, or model changes needed to pass, retest, and refactor iteratively.
  • When benchmarks conflict, decide explicitly: accept partial pass targets, split into specialized agents (plus triage), or refactor the agent’s instructions from first principles.
  • Prefer tool guidance in the tool’s name/docstring over prompt clutter; rename tools and write clear docstrings; keep prompts lean and role focused.
  • Add evaluation agents to score complex, natural-language outputs with typed results (e.g., pass/fail plus feedback), avoiding brittle string matching and enabling programmatic gating.
  • Grounding agents are essential for RAG; they verify that answers are supported by the provided context or citations. On failure, they can regenerate, block with a static response, or pass grounded feedback forward.
  • Guardrails operationalize grounding. Wrap agents with output guardrails that trip on ungrounded answers and surface feedback and flags for policy (retry, block, or annotate).
  • Rubrics turn subjective quality into criteria and scales. Use them with critic agents for high-variance generation (images, reports, graphs). Loop generation critique until a passing score or attempt limit.
  • Because LLMs are stochastic, benchmark for stability, not just accuracy, by rerunning tests and watching variability, latency, and token use.
  • Observability is nonnegotiable: OpenAI Traces show every tool call and LLM turn; Arize Phoenix (OpenTelemetry) adds projects, sessions, metrics, costs, experiments, and evaluators.
  • Instrument Phoenix cleanly: set the collector endpoint, replace the default processors, register a tracer, and wrap runs with named traces. Attach sessions and metadata for filtering and cohort analysis.
  • Build datasets from spans, run experiments/evaluators, and use annotations to capture structured human feedback. Feed these signals back into prompts, tools, and policies.
  • Production rule: never promote agents without active evaluation/feedback loops, benchmarks, grounding/guardrails, critics with rubrics, tracing, and monitored KPIs (latency, cost, quality) working together.
