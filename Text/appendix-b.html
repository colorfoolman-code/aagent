appendix B  Node.js setup for local MCP servers

Many Model Context Protocol (MCP) servers are distributed as Node.js packages on the public npm registry. The most convenient way to run one of these servers locally is with npx, a small command-line tool that ships with Node.js. Given a package name, npx downloads the package if it is not already cached, resolves its executable entry point, and runs it, all in a single command. That makes it possible to point an MCP client such as Claude Desktop, an IDE plugin, or a custom agent at a fresh MCP server without writing any installation scripts of your own.

Before you can take advantage of any of this, you need a working Node.js installation on your machine. This appendix walks through that setup end to end. It is organized into four sections that follow the natural setup order: installing Node.js, verifying that node and npx are on your path, running an MCP server with npx, and, finally, troubleshooting the most common problems and keeping your installation healthy over time.

B.1 Installing Node.js

Node.js is the JavaScript runtime that npx depends on, and it bundles both npm (the package manager) and npx in a single installer. For the MCP servers covered in this book, install the current long-term support (LTS) release of Node 20 or later. The following subsections show the recommended installation path for each major operating system.

B.1.1 Installing Node.js on Windows

On Windows, the simplest path is the official installer:

  1. Open https://nodejs.org in a browser and download the LTS installer for Windows.
  2. Double-click the downloaded .msi file and accept the defaults. Leave the Automatically Install the Necessary Tools option enabled if you plan to build native modules. Otherwise, it is safe to clear it.
  3. Close and reopen any open command prompts or PowerShell windows so they pick up the updated PATH environment variable.

If you prefer to manage multiple Node versions side by side, install nvm-windows from https://github.com/coreybutler/nvm-windows instead. Then run nvm install lts, followed by nvm use lts.

B.1.2 Installing Node.js on macOS

On macOS, the recommended path is Homebrew, which keeps Node up to date alongside your other developer tools. From a terminal, run

brew install node

If you do not have Homebrew installed, follow the instructions at https://brew.sh first. Alternatively, you can download the macOS .pkg installer from https://nodejs.org and run it like any other macOS installer.

B.1.3 Installing Node.js on Linux or WSL

On Linux and Windows Subsystem for Linux (WSL), the recommended path is nvm, the Node Version Manager. Unlike the distribution’s system package, nvm lets you switch Node versions on a per-project basis without using sudo. Install it with

curl -o- https://raw.githubusercontent.com/nvm-sh/nvm/v0.39.7/install.sh | bash

Close and reopen your terminal so the new shell configuration is picked up; then install and activate the LTS release of Node:

nvm install --lts
nvm use --lts

If you prefer to use your distribution’s package manager instead, the Node.js project publishes official APT and DNF repositories at https://github.com/nodesource/­distributions. Follow the instructions there for your specific distribution.

B.2 Verifying your Node and npx installation

Once Node is installed, it is worth taking a moment to confirm that everything is on your PATH and to develop a mental model of how npx handles the packages it runs. The following subsections cover the version check and a brief tour of the npx cache.

B.2.1 Checking the installed versions

Open a new terminal window and run the following three commands:

node --version
npm --version
npx --version

Each command should print a version number. node --version should report v20 or later, and npm --version and npx --version should each report a number close to 10. If any of the three commands returns a Command Not Found error, the installer’s PATH update did not take effect. Close and reopen your terminal (or your whole shell session) and try again.

B.2.2 How npx finds and caches packages

When you run a package with npx, it does roughly the following:

  • It looks for the package in your local node_modules folder. If it finds the executable there, it runs that copy.
  • If the package is not installed locally, it looks in the global npm cache at ~/.npm/_npx (or the equivalent on Windows). If the requested version is already cached, it runs the cached copy.
  • If the package is not cached either, npx downloads it from the npm registry, places it in the cache, and runs it.

The practical consequence is that the first run of an MCP server with npx takes noticeably longer than subsequent runs because it spends time downloading the package. From the second run onward, npx simply launches the cached copy.

TIP The -y flag (covered in the next section) tells npx to skip the interactive “Need to install the following packages, ok?” prompt. MCP clients that spawn an MCP server as a subprocess do not have a way to answer that prompt, so always include -y when configuring a client.

B.3 Running an MCP server with npx

With Node installed and verified, you are ready to run an MCP server. The following subsections break the npx command into its parts, then walk through a concrete example using the official filesystem MCP server, and finally show how to wire that server into an MCP client.

B.3.1 Anatomy of the npx command

A typical command to launch an MCP server with npx has four parts:

npx -y <package-name> [server-arguments...]
  • npx—The launcher that ships with Node.js.
  • -y—Short for --yes. Accepts the install prompt automatically, which is required when an MCP client spawns the server as a subprocess.
  • <package-name>—The npm package that ships the MCP server, for example, @modelcontextprotocol/server-filesystem.
  • [server-arguments...]—Any arguments the MCP server itself accepts. These are passed through to the server process. The filesystem server, for instance, takes one or more directory paths that it will allow the MCP client to read and write.

B.3.2 Running the filesystem MCP server

As a concrete example, the official filesystem MCP server lives at @modelcontextprotocol/­server-filesystem on npm. To run it against a single directory, open a terminal and run

npx -y @modelcontextprotocol/server-filesystem /path/to/allowed/directory

On Windows, replace the Unix-style path with a Windows path, for example:

npx -y @modelcontextprotocol/server-filesystem C:\Users\you\Documents

The first run downloads the package and may take a few seconds; subsequent runs start almost immediately. Once the server is running, it communicates with its client over standard input and output using the MCP protocol. Running it directly in a terminal is mainly useful as a sanity check: the server will print a startup banner and then sit waiting for MCP messages on stdin. Press Ctrl-C to stop it.

B.3.3 Wiring the server into an MCP client

MCP clients launch their servers as subprocesses, which means you do not normally run the npx command yourself—you describe it to the client in a configuration file. The exact location of that file depends on the client. Claude Desktop, for example, reads from a JSON config file in your user profile. The entry for the filesystem server looks like the following:

{
  "mcpServers": {
    "filesystem": {
      "command": "npx",
      "args": [
        "-y",
        "@modelcontextprotocol/server-filesystem",
        "/path/to/allowed/directory"
      ]
    }
  }
}

Note that the command field is just npx and the package name appears as one of the args entries, with -y listed first to suppress the install prompt. This same pattern works for any MCP server published on npm: change the package name and the trailing arguments to match the server you want to run.

B.4 Troubleshooting and keeping Node healthy

Most problems with npx-launched MCP servers fall into one of a few categories. The following subsections cover the problems you are most likely to see, how to clear the npx cache when a stale copy is causing trouble, and how to keep Node itself up to date.

B.4.1 Common issues

Following are the problems you are most likely to see:

  • "npx: command not found"—Your shell cannot see the Node binaries. Close and reopen your terminal so the updated PATH is picked up. On macOS and Linux, confirm that nvm use --lts was run in the current shell, or add it to your shell startup file.
  • EACCES or permission errors during install—You installed Node with sudo, and the cache is now owned by root. The cleanest fix is to remove the system-wide install and switch to nvm, which installs Node into your home directory.
  • MCP client reports the server exited immediately—Run the same npx command directly in a terminal. The server’s error message will appear there but is normally swallowed by the client.
  • MCP client hangs at startup—You almost certainly forgot the -y flag, and npx is waiting on an install confirmation prompt the client cannot answer.

B.4.2 Clearing the npx cache

If you suspect npx is running a stale copy of an MCP server, for example, after a package publishes a fix you want to pick up, clear the cache and let it redownload on the next run:

npm cache clean --force

To pin a specific version on the next run instead, append @<version> to the package name, for example, npx -y @modelcontextprotocol/server-filesystem@latest. This forces npx to resolve the requested version against the registry before running.

B.4.3 Updating Node

Node ships a new LTS release roughly once a year. To stay on the current LTS, update periodically using the same tool you installed Node with:

  • On Windows with the official installer, download the latest LTS .msi from https://nodejs.org, and run it. The installer upgrades the existing installation in place.
  • With Homebrew on macOS, run brew upgrade node.
  • With nvm on Linux, macOS, or WSL, run nvm install --lts followed by nvm alias default lts/* to make the new version the default for future shells.

After upgrading, run the three version checks from section B.2.1 again to confirm the new versions are on your PATH.
