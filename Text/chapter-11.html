11.1 Field-tested tips organized by the five agentic layers

Throughout this book, we have explored agents using the five functional layers of agents: persona, tools and actions, reasoning and planning, knowledge and memory, and evaluation and feedback. Figure 11.1 reminds us of what happens at each layer.

Let’s go back through these layers now, looking at practical tips for each one.

11.1.1 The core layer: Persona

Your agent’s personality shapes all downstream choices (tools, memory, planning). Treat the persona as an API contract, not a piece of prose. A well-crafted persona (with clear prompt instructions) can make a key difference in how your agent behaves at every level. Here are four guidelines to keep in mind when building the core of your agent, the persona:

  • Define a crisp role and boundaries. State what the agent does and does not do; repeat critical rules at the top and bottom of the instructions to counter recency and drift. Provide an explicit “I don’t know” off-ramp.
  • Keep scope narrow. Specialized, single-responsibility agents outperform “do-­everything” bots and are easier to test and cost optimize.
  • Prefer structured output. When the agent interacts with other code or agents, return a JSON response that matches a schema (Pydantic/dataclass). It cuts parsing bugs and token bloat.
  • Use dynamic instructions. Inject runtime facts (date, org, user) via a function rather than hardcoding. Be careful not to overuse dynamic injection; keep the facts relevant to the agent’s use case and goal. Overinjection can cause token bloat, agent confusion, and poor responses.

The following listing incorporates these four principles and provides examples of how you can consistently use them to build your agents.

Listing 11.1 01_core_persona_tips.py
from pydantic import BaseModel, Field
from agents import Agent, Runner
from datetime import date

class Answer(BaseModel):    #1
    """Machine-readable answer format."""
    answer: str = Field(..., description="Concise, user-facing answer")
    citations: list[str] = Field(default_factory=list)
    confidence: float = Field(..., ge=0, le=1)

def core_instructions(ctx, agent) -> str:    #2
    today = date.today().isoformat()    #3
    return (
        f"You are SupportMentor, a helpful domain assistant. Today is {today}.\n"    #4
        "Always:\n"
        "1) Answer concisely; 2) Prefer retrieved context; 3) If context is missing, say you don't know.\n"
        "Output must be valid JSON matching the Answer schema.\n"
        "Never: make policy exceptions or invent facts."
    )

core_agent = Agent(
    name="SupportMentor",
    instructions=core_instructions,   
    output_type=Answer                
)

input = "What's our refund window for accessories?"
result = Runner.run_sync(core_agent, input)
print(result.final_output)
#1 Uses a typed data class to define the output of the agent
#2 Keeps the agent scope narrow and focused
#3 Uses dynamic input in prompt instructions
#4 Keeps the persona role focused and well defined

This simple code example demonstrates the four principles in action. Use these four guidelines when creating your agents.

11.1.2 Tools and agent actions

Tools are the agent’s hands and senses. Good tools can empower an agent, while poor tools can make that agent equally ineffective. There are five essential guidelines to follow when building tools, consuming tools from other MCP servers, or using agents as tools:

  • Use single-responsibility tools with crisp docstrings and typed params. Models learn to use tools from descriptions and schemas. The tool’s description, name, and inputs must provide clear guidance on how to use it.
  • Prefer function tools for your code and APIs. Decorators automatically generate schemas from type hints/docstrings, making it easier to test and reuse.
  • Control when tools run. Use model/tool settings to force or forbid tools for certain turns; stop on the first tool when a single API result is enough. Outline in the agents’ prompt when and how to use tools to support this pattern.
  • Use prebuilt tools where sensible (code, web, file search). Use hosted tools and hardened MCP servers to accelerate capability. Do your due diligence to be sure any MCP server you consume is safe, robust, and focused.
  • Plan for failures. Add timeouts/retries and friendly fallbacks. Tools can fail, so make sure the agent understands why a tool failed and potential ways to correct it.

The next listing shows a simple tool-using agent that incorporates all five guidelines and demonstrates best practices.

Listing 11.2 02_tool_action_tips.py
from agents import (
    Agent, 
    Runner, 
    function_tool, 
    ModelSettings
)
import json

def _failure_error_function(context, e) -> str:        #1
    return json.dumps({"status": "error", "message": str(e)})

@function_tool(
    failure_error_function=_failure_error_function)    #1
def lookup_order(order_id: str) -> dict:   #2
    """Check order status by ID. Use when the user asks about their order."""         #2
    if not order_id.startswith("ORD-"):
        raise ValueError("Invalid order id format")
    return {"status": "shipped", "eta_days": 3}


tooling_agent = Agent(
    name="ToolingAgent",
    instructions="Use tools when needed; respond with JSON.",    #3
    tools=[lookup_order],
    model_settings=ModelSettings(
        tool_choice="auto",    #3
        parallel_tool_calls=True,     #3
    )
)
print(Runner.run_sync(
    tooling_agent, 
    "What's the status of order ORD-123?"
).final_output)
#1 Plans for failures by capturing formatting and recovering gracefully from tool errors
#2 Single-responsibility tools with crisp, well-defined docstrings and type params
#3 Controls when and how tools run

The key takeaway when building and consuming tools is to ensure they are focused and well defined. This applies equally to MCP servers. Remember, every tool an agent consumes adds overhead to every LLM call the agent makes.

Tool bloat

As a rule, always keep tool sets small, and when using MCP servers, be conscious of how many tools the server exposes. Remember, every tool carries with it a description of how to use it, which adds tokens and context to the LLM message. To avoid confusing your agents and to reduce costs, keep tools focused on the agent’s role.

11.1.3 Reasoning and planning

Multistep work needs a plan, a loop, and stop conditions. Reasoning and planning are the cornerstones of agentic behavior and can make the difference between achieving goals and failing. Although most foundational consumer models use reasoning today, it is often best to understand and control how that reasoning is used. The following tips can help you use reasoning within your agents:

  • Adopt ReAct for nontrivial tasks. Alternate between thinking and action; inspect observations; then proceed. Use the ReAct or chain-of-thought prompt instruction patterns to guide your agent’s thought process.
  • Plan-then-execute for big goals. Draft a checklist, and record the plan using tools like sequential thinking servers. Allowing your agent to construct thoughts gives it time to think and better solve complex tasks.
  • Limit iterations. Cap the number of turns to prevent runaway loops; fail safely with a helpful message.
  • Perform self-review before final. Add a quick reflexive pass to catch obvious mistakes.

For simple one-shot tasks, you may want to avoid reasoning altogether in the agent’s instructions or within the LLM by turning the model’s reasoning down or off.

Let’s see these tips in practice within a simple planning agent that has access to the reference MCP sequential thinking server.

Listing 11.3 03_reasoning_planning_tips.py
from typing import Literal
from pydantic import BaseModel
from agents import Agent, Runner
from agents.mcp import MCPServerStdio

MAX_TURNS = 3  #1

thinking_srv = MCPServerStdio(    #2
        name="sequential-thinking",
        params={
            "command": "npx",
            "args": ["-y", "@modelcontextprotocol/server-sequential-thinking"],
        },
    )

class Answer(BaseModel):
    status: Literal["ok", "needs_followup"] = "ok"
    checklist: list[str] = []
    summary: str
    sources: list[str]

instructions = f"""
You are a planner-executor.
If the message starts with 'PLAN ONLY', 
return only the checklist (no actions).
1) Plan→Execute: draft a concise 3–5 item checklist, then execute.    #2
2) ReAct: Thought→Action(tool)→Observation;    #3
inspect each observation before continuing.
3) Limit: stop after at most {MAX_TURNS} tool calls;    #1
if reached, set status='needs_followup' and return best effort.
4) Self-review: before final, catch obvious mistakes,     #4
ensure the question is answered, and cite sources.
Use seq_think between actions to decide the next step. 
Return Answer JSON only.
"""

async def main():
    agent = Agent(
        name="Planner", 
        instructions=instructions, 
        mcp_servers=[thinking_srv], 
        max_turns=MAX_TURNS,
        output_type=Answer)

    async with thinking_srv:
        question = "Summarize our refund policy and cite relevant internal docs."
        plan = await Runner.run(agent, f"PLAN ONLY. Question: {question}")
        print(plan.final_output.checklist)

        result = await Runner.run(agent, question)
        print(result.final_output)

if __name__ == "__main__":
    import asyncio
    asyncio.run(main())
#1 Limiting the number of iterations the agent can perform
#2 Plans then executes the big goals
#3 Employs the ReAct and CoT or other reasoning strategies
#4 Performs a self-review before final output

The ability to encourage and control reasoning and planning can limit the external thoughts of an LLM. Today, most commercial LLMs have built-in reasoning capabilities, which can work well for general problems. But left to their own devices, reasoning models can become quite unpredictable if not adequately controlled. Don’t assume an LLM with reasoning will always do the right thing; many times, it won’t.

11.1.4 Knowledge and memory

Retrieval is crucial to knowledge and memory, both of which rely on the ability to locate relevant information quickly. When we look at optimizing knowledge or memory, we always start with retrieval. Here are some key conventions to follow when working on retrieval and the practice of finding relevant information:

  • Consider RAG as a first-class capability. Add a retrieval tool over your knowledge base (vector store plus metadata filters) instead of stuffing documents into prompts.
  • Use sessions versus long-term memory. Use session threads for short-term context; persist user facts and preferences in a vector/DB store, and retrieve them selectively. Prune aggressively.
  • Optimize retrieval at scale. Use ANN indexes (HNSW/IVF), shard by domain, and filter by metadata (e.g., product, version, date).
  • Employ hybrid search patterns. Don’t rely on a single pattern, such as vector (semantic) search. Instead, augment your strategies with keyword search, graph hierarchical search, and other patterns.
  • Choose embeddings deliberately. Balance quality, dimensions, and cost; consider domain-specific or multilingual variants to optimize your approach. Embedding size can be crucial when allocating storage.
  • Chunk wisely and ground answers. Prefer semantically coherent chunks, and instruct the answerer to use only retrieved context (and say “don’t know” when the answer is absent).
  • Keep data fresh and partitioned by role and type. Update your KB routinely, and isolate sensitive departments, content, or tenants. Don’t allow users access to contexts they shouldn’t have. Even if you think your basic one-index RAG will support your use case, expect that to change, and plan to implement role/type partitioning.

Listing 11.4 demonstrates these best practices in a straightforward single-agent example that uses knowledge and memory. The code assumes a generic vector database, so your implementation may vary accordingly.

Listing 11.4 04_knowledge_memory_tips.py
from agents import Agent, Runner, SQLiteSession, function_tool

kb = load_vector_kb(     #1
    embedding_model="text-embedding-3-small",       #2
    index="HNSW",                                
    shards=["product", "policy", "engineering"], )

@function_tool
def retrieve(query: str, product: str|None=None, version: str|None=None,
             date: str|None=None, role: str|None=None, tenant: str|None=None) -> str:
    """Return grounded snippets using metadata filters."""
    return kb.query(query=query, k=5,
        filters={"product": product, "version": version, "date": date,
                 "role": role, "tenant": tenant})    #3

@function_tool
def remember(user_id: str, fact: str) -> str:
    """Persist long-term user fact in vector memory; prune aggressively."""
    kb.upsert(text=fact, metadata={"user_id": user_id, "kind": "preference"}, 
    ttl_days=90); return "ok"    #3

agent = Agent(
    name="Support",
    instructions=("Use ONLY retrieved context; cite chunk ids; if absent #4
    say 'I don't know'."),    #4
    tools=[retrieve, remember],
)
session = SQLiteSession("u42-chat")    #5

kb.ingest("docs/*.md", chunking="semantic",
          partition_by=["role", "tenant", "product", "version"])    #3
print(Runner.run_sync(
    agent, 
    "Can I use the beta API on v3.2? (tenant=acme)", 
    session=session))
#1 Uses RAG as a first-class feature of the agent
#2 Chooses and optimizes embeddings
#3 Keeps data fresh and partitioned by role
#4 Grounds answers and makes sure agent uses retrieved knowledge
#5 Uses session and long-term memory for better results

Memory can be a foundation for not only remembering the user’s conversation. It can also include memories and experiences from other agents or even conversations. Knowledge is key to improving agent context, but a complete memory solution can help an agent learn and adapt over time.

11.1.5 Evaluation and feedback

You don’t improve what you don’t measure. At the heart of everything you do, log and measure everything internal and external to your agents. This can assist with debugging and incident resolution, and it can also help you optimize and improve your agents. You may not want to build all the recommendations here initially, but you will want a minimal setup that includes basic logging, tests, and simple guardrails. The fuller guidelines are best practices for production systems.

Use the following best practices to help you use evaluation and feedback in agents:

  • Trace everything. Record prompts, tool calls, token counts, latency, and outcomes. Use the SDK’s built-in tracing dashboard or Phoenix for a global view of everything. Wire logs to your observability stack.
  • Automate evals. Maintain curated test sets and LLM-as-judge checks; run them on each prompt or model change to track accuracy, safety, and resolution rates. Again, Phoenix can handle all these evaluations.
  • Human-in-the-loop (HITL). Humans are your best source of feedback. Add systems that capture human user feedback, then evaluate it in detail and optimize.
  • Guardrails and moderation. Enforce content policy and schema validation at inputs and outputs, as well as around high-risk tools. Critic and guardrail agents can help identify bad output and address it accordingly.
  • Iterate like DevOps (AIOps). Measure and capture everything, observe it, and then optimize. Remember to include tool calls and other system interactions for systems your agents may rely on, such as databases, indexes, and other relevant components.

11.2 Tips for building a customer support agent

We will now examine specific tips for the most popular agent patterns used today, beginning with the customer support agent. This form of agent is often used to assist customers with support questions, but it can also be easily adapted to support aninternal-­facing role. Done well, these agents can augment expensive customer support roles by triaging support tickets, answering basic questions, and escalating critical events.

For this type of agent, the five agent layers map respectively to the following: persona = support role; tools/action = APIs/lookup/escalation; reasoning/planning = triage logic and HITL escalation; knowledge/memory = RAG over manuals; eval/feedback = logs/HITL.

Support agents need grounded answers, safe actions, and graceful escalation. These agents are often on the front lines for customer support, feedback, and complaints. As such, you should make them robust, professional, and helpful by using the following guidelines:

  • Narrow the charter. Start with a bounded set of intents (orders, returns, status) and add domains over time. Keep these agents light and focused so they are more responsive and less prone to errors or hallucinations.
  • Ground every answer. Add a RAG tool over manuals, policies, and release notes. In the prompt instructions, use the phrase “use only the provided context.” But take this a step further and use grounding agents to ensure that contextual answers are always grounded.
  • HITL as a feature. Expose an escalate_to_human tool; route complex or angry cases and large refunds. Provide a mechanism that allows customers to give direct feedback on how well the agent addressed their problems.
  • Identity and access. Verify user identity before exposing account data; follow least privilege for tools. Grant the agent the user’s role and associated tools to control access.
  • Resilience. Implement retries, fallbacks to secondary models/tools, timeouts, and friendly failure messages. A robust agent shows users that care has been taken to address their problems, increasing their confidence.
  • Caching and rate limits. Cache popular answers (“refund policy”) and throttle external APIs to protect costs and reliability. Use caching wisely, and avoid the “store everything” mentality.
  • Transparent traces. Keep per-conversation traces to audit decisions, including searches performed and sources cited. This may involve pulling traces from Phoenix or duplicating them for support, auditing, and data capture purposes.

Figure 11.3 demonstrates the implementation of a standard customer support agent/agentic system. As you can see, what we describe as one agent is actually multiple agents, six in this case, performing various roles and working together.

Figure 11.3 A complete customer support agentic system workflow

In a standard customer support workflow, after the user asks a question, a triage agent determines whether it can be resolved or needs to be passed on to a human. If it can assist the user, the flow next moves to a retrieval agent. This agent pulls relevant information related to the user’s question and generates comments, a summary, or an answer to the original question. This output is then checked by a grounding agent, which verifies that the output is fully grounded in the context provided.

The grounding agent may also determine whether action is required and, if so, call a scoped business API. If the API is called, a guardrail agent validates and confirms that the output is expected. Finally, an answer agent takes the results of the retrieval and any API calls and provides them as an answer to the user. The user can then submit thumbs-up or thumbs-down feedback to the system based on the quality of the answer and the overall interaction.

11.3 Tips for building a RAG agent system

RAG agents are often the backbone of other agentic systems. As we saw in the previous section, a RAG agent can be embedded into a larger agentic system, such as a customer support agent. Rarely do we see a single RAG agent providing direct output to users.

Retrieval is the engine; agentic control adds routing, critique, and tooling around it. But just like the customer support example, a RAG agent system is composed of multiple agents, each with a specific role within a larger RAG workflow. Use the following tips to help guide the development of such agents:

  • Use agents only when needed. If a one-shot RAG call works, skip the orchestrator. Add agents for routing (branched retrieval), diagnostics, or actions. Focus on keeping only the agents that are essential to the larger workflow.
  • Design modular agents. Triage (router) > retriever > answerer; optionally, a critic for corrective retrieval (CRAG).
  • Optimize retrieval. ANN indexes, metadata filters, domain-tuned embeddings, and reranking. Include hybrid retrieval options to find a wide variety of search forms.
  • Grounding discipline. Force “use only context” and require citations or source excerpts. Include specialized grounding agents to evaluate answer context.
  • Observability and evals. Log retrieval recall, answer accuracy, and cases where the system should have said “I don’t know.” Tracking retrieval calls can help identify pain points in the data search process. In almost all cases, you want your agent system to reply with “I don’t know” rather than provide a false answer with confidence.

11.4 Tips for building a deep research agent system

Deep research agents mix open-ended web exploration, iterative planning, and synthesis from many sources. Virtually all major LLM providers (ChatGPT, Claude, and Gemini) support such agents. If you need a deep research agent to search other sources of information, such as knowledge bases, internal system databases, and document stores, we generally recommend building an internal version.

Building an internal deep research agent can be complex and require developing a team of specialized agents. Use this type of agent only when you know simpler agent systems may lack the ability to solve complex problems. Here are our general best practices for developing these types of agentic systems:

  • Two-tier orchestration—A research planner (brain) delegates to stateless workers (web searcher, extractor, analyst, summarizer). Keep workers tool-like (no long memory).
  • Tool policy controls—Force the planner to call the retrieval and web tools for facts. Forbid direct answers to claims without sources.
  • Self-critique and fact checks—Add a critic pass to check coverage, contradictions, and missing perspectives before finalization.
  • Streaming UX—Stream partial findings and the evolving outline. This improves perceived latency and supports “checkpoint” approvals. This could be a static list of messages, such as “Now searching or thinking,” or the actual reasoning thoughts the agent is outputting.
  • Caching and budgets—Cache repeated queries and set per-run token budgets with alerting. Throttle web/API calls. This can be a great asset when agents repeat the same query, but it can also hinder search. Therefore, be sure to clear the cache at regular intervals to avoid returning stale data.

Listing 11.7 provides a simple example of an agent brain (research planner) with several worker (hands) agents. At the top of this code, we create several tools to search, extract, and analyze search results. These may be direct tools or wrappers for agents that act as tools. Determining whether a tool should be a tool or an agent depends on what decisions the tool makes. Tools that require decision-making are agents that use tools.

#2 These could be tools or specialized agents, depending on details and required decisions.

After the research agent searches for and finds enough context, it hands off the results to a critic agent. The critic agent then determines whether the retrieved context answers the initial question. If the critic agent determines that it does, it passes the search context to a writer agent to output an answer. But if the critic agent determines that the question needs more context, it returns the search to the researcher.

Figure 11.5 shows the entire deep research agent pattern from the previous code example. Here, the research planner agent acts as the brain to the various agents’ hands (web search, extractor, and analyst agents). After the workers have found relevant context, they return the results to the planner. The planner then passes the results to a critic, who determines whether there is enough information to answer the initial question. If there is not enough information, the critic returns the result to the planner and requests additional context.

Figure 11.5 Implementation of the deep research agent system

Likewise, if the critic determines that enough information has been found, it passes the results to the final report agent. This final agent constructs the answer or report, ensuring that all previously returned references are appropriately cited within the answer. Requiring the agent to cite answers properly also provides direct grounding in the context found earlier.

Summary

  • Treat agent design as five stacked layers: persona, tools and actions, reasoning and planning, knowledge and memory, and evaluation and feedback. Optimize each layer independently, then integrate.
  • Write the persona as an API contract, not prose: a clear role, boundaries, and an explicit “I don’t know” off-ramp.
  • Keep the scope narrow (single responsibility) for higher accuracy and easier testing­­/cost control.
  • Prefer structured, typed outputs (Pydantic/dataclass JSON) to eliminate parsing brittleness.
  • Use dynamic instructions (inject date/org/user) at runtime to avoid stale facts.
  • Build single-responsibility tools with crisp names, docstrings, and typed parameters. The model learns tool use from these schemas.
  • Control when tools run (e.g., tool_choice, parallel tool calls); stop early when one call suffices.
  • Use prebuilt or hosted tools where sensible, but be selective.
  • Plan for failures: timeouts, retries, graceful error payloads, and fallbacks.
  • Adopt ReAct or chain-of-thought patterns for nontrivial tasks.
  • Plan, then execute: draft a short checklist before acting; consider a lightweight “thinking” server or step.
  • Cap iterations to prevent runaway loops. Signal needs_followup on budget/turn limits.
  • Add a quick self-review pass before finalizing to catch obvious mistakes.
