9 Understanding the agentic loop

This chapter covers

  • Peeling back the three agentic loop layers
  • Looping with a deep research agent
  • Multi-agent orchestration loops
  • Building collaborative agentic loops

Way back in chapter 1, we explored the core agentic loop pattern, which we referred to as the SPAL (sense-plan-act-learn) process loop. In this chapter, we look beyond the internal agent loop to looping patterns that extend outside the agent. These patterns are used to formulate long-horizon, goal-driven agents, such as those involved in deep research or, more collectively, in what’s called the agent collaboration workflow.

Using agentic looping to empower agents introduces new levels of command and control in both single- and multi-agent systems. This chapter explores the three layers of the agent loop. These range from the internal loop (SPAL) we already know about to long-horizon goal execution to meta-guided looping in multi-agent systems. Along the way, we look at practical applications of each layer and how you can introduce these patterns into your agentic workflows.

9.1 Peeling back the three agentic loop layers

The internal loop (SPAL) is the first, or core, layer of an agent. This loop allows an agent to iterate, discover, reason, and execute tasks to complete goals. But two more agentic loop layers can extend the work of the agent: layer 2, the task loop, and layer 3, the meta loop.

9.1.1 Layer 1: The inner loop (sense-plan-act-learn)

The level-1 agentic loop works by wrapping the agent’s execution in a controlled cycle that repeats until the agent’s goal is satisfied or a termination condition is met. Figure 9.1 illustrates the layer-1 core agentic loop architecture. As you can see, the agent begins with a goal and senses the current internal state (including any accumulated context from prior iterations). It then plans its next action, executes that action using its tools, evaluates the result, and updates the internal state. It then decides whether the goal has been met and, if not, loops back, carrying forward everything it has learned.

Figure 9.1 The core agentic loop. The agent cycles through sense, plan, act, and evaluates the steps until the goal is satisfied or a termination condition is triggered. Internal state accumulates across iterations, giving each cycle more context than the last.

What makes this loop agentic, rather than just a while loop in code, is that the agent itself makes decisions at each step. The agent decides how to complete the goal, which tool to call, whether the result is good enough, and when to stop. The developer defines the goal, provides the tools, and establishes the boundaries, but the agent drives the iteration.

From the figure, notice that some important terminology has been identified. The goal, what the agent will undertake; the plan, how the agent will execute; the tool, how the agent will act; the state (internal), how the agent keeps context (memory); and the sense/decision, how the agent determines when it is done. At the level-1 layer, all these elements are internal to the agent.

Every agentic layer-level loop rests on these core elements: the goal, the plan (iteration strategy), the state, and the decision (termination condition). Getting this right is the difference between an agent that converges on excellent output and one that runs forever or gives up too early.

9.1.2 Layer 2: The task loop

Layer 2 of the agentic loop is about externalizing the core elements (goal-­­plan-state-decision) outside the agent. This extends the goal horizon an agent can work toward, from simple goals to very complex ones. Figure 9.2 shows examples of short- and long-horizon goals we may ask an agent to perform. It also extends the concept of the layer-1 agentic loop to the layer-2 agentic loop.

Figure 9.2 Comparison of short- and long-horizon goals. You can see how this process requires promoting the single-agent internal loop to the level-2 external task-based agentic loop.

We move to a secondary external loop to make room for long-term plans and extended state persistence. Internally, the agent still maintains a plan and internal state, but these pieces are short-lived within the agent’s internal cycle. To accomplish long-horizon goals, the agent system needs to persist the plan and state externally.

By externalizing the agent’s plan and state, a single agent can work across multiple short-horizon goals to achieve long-horizon goals such as deep research. We do this not only because we don’t want to overwhelm the LLM’s context window. We do it also because general-purpose LLMs, by design, are not well suited to long-running iterations. More recently, agentic-focused LLMs have started becoming popular, but they still face the large-context-window problem.

The mechanisms that power the second layer are generally programmatic, deterministic constructs that wrap the agent. As we will see later in the chapter, planning may involve a long-running, sequential-thinking server, and state may be stored in process memory or a database, where the decision is a check in code and the tool is the agent itself.

9.1.3 Layer 3: The meta loop

The third layer, the meta-agentic loop, is an agent or agents that control the internal layer-1 or layer-2 processes. The key difference between layers 2 and 3 is that the second layer is often directed by code, while an agent or agents control the meta layer. Figure 9.3 demonstrates the incorporation of the third meta layer, which is controlled by an agent orchestrator or by a collaboration of agents.

Figure 9.3 Comparison between level 3 of the agentic loop using an orchestrator controller and the more free-form collaboration pattern

Because an agent controls the third meta layer, its placement determines the loop’s subtype: either orchestration or collaboration. In an orchestration-controlled meta loop, a single delegating agent encapsulates the decide, state, and plan elements within its own internal loop, using the delegation subagents as tools. When the decision agent or agents become part of the loop, it becomes a collaboration of agents that may or may not share state and plan components, depending on the use case.

Because we have already extensively covered the internal agent loop, our focus for the rest of the chapter will be on implementing the higher forms of the agentic loop: the layer-2 task loop and both forms of meta loop (layer 3).

9.2 Layer 2: Looping with a deep research agent

The deep research agent is probably the best-known implementation of the layer-2 agentic loop, where the word “deep” refers to the more extensive search an agent performs to complete longer-horizon, in-depth research goals. Research agents have become widespread, and every foundational model provider (Google Gemini, Anthropic Claude, and OpenAI ChatGPT) provides some form of deep research agent.

The difference between a good agentic loop and a runaway cost generator comes down to three things: how you manage state between iterations, how you define termination conditions, and how you connect the agent to external tools. Get these right, and you have a system that converges reliably on high-quality output. Get them wrong, and you have a system that burns through tokens in circles.

9.2.1 Creating the initial state and plan

The flow starts by initializing the ResearchState and ResearchPlan objects, as shown in the next listing. These objects maintain an external state and a plan outside the agent’s execution and are shared across each iteration of the agent loop.

Listing 9.1 01_research_state_plan.py (research state and plan)
from pydantic import BaseModel, Field

class SubTopic(BaseModel):
    """A single sub-topic within the research plan."""
    name: str
    status: str = "pending"  # pending | in_progress | complete
    notes: str = ""

class ResearchPlan(BaseModel):
    """Strategic plan that guides the research process."""
    sub_topics: list[SubTopic] = Field(default_factory=list)
    strategy_notes: str = ""

    def to_context(self) -> str:    #1
        return str(dict(
            sub_topics=[
                dict(name=st.name, status=st.status, notes=st.notes)
                for st in self.sub_topics
            ],
            strategy_notes=self.strategy_notes,
        ))

    @property
    def progress_summary(self) -> str:    #2
        if not self.sub_topics:
            return "No plan yet"
        total = len(self.sub_topics)
        complete = sum(1 for st in self.sub_topics
                       if st.status == "complete")
        in_progress = sum(1 for st in self.sub_topics
                          if st.status == "in_progress")
        return (f"{complete}/{total} complete, "
                f"{in_progress} in progress")

class ResearchState(BaseModel):    #3
    goal: str = ""
    findings: list[str] = Field(default_factory=list)
    sources_consulted: list[str] = Field(default_factory=list)
    follow_up_questions: list[str] = Field(default_factory=list)
    plan: ResearchPlan = Field(default_factory=ResearchPlan)
    iteration_count: int = 0
    max_iterations: int = 10
    status: str = "in_progress"

    @property
    def should_continue(self) -> bool:    #4
        return (
            self.status == "in_progress"
            and self.iteration_count < self.max_iterations
            and len(self.follow_up_questions) > 0
        )

    def to_context(self) -> str:    #5
        return str(dict(
            goal=self.goal,
            findings=self.findings,
            sources=self.sources_consulted,
            pending_questions=self.follow_up_questions,
            plan=self.plan.to_context(),
            iteration=self.iteration_count,
            remaining=self.max_iterations - self.iteration_count,
        ))
#1 A helper function for converting a plan to a string context for consumption by an LLM
#2 Property of the plan that returns a context string summary of the plan execution
#3 A state object that can be carried from one agent iteration to another
#4 Property to determine if the agent should continue research
#5 Helper function to convert state to a context string for consumption by an LLM

The ResearchState is essentially the shared memory that tracks each agent iteration in the loop. At the first iteration, the state will be empty, but it will quickly accumulate information as the agent iterates. Likewise, the ResearchPlan holds the strategy the agent will use in each iteration. In this example, the plan will be updated as the agent iterates through observations. It also increases its understanding of how best to conduct the search/research.

The key design decision in listing 9.1 is the to_context method, which serializes the accumulated state/plan into a dictionary string that the agent can consume. By controlling what the agent sees at each iteration, we can manage context window usage and keep the agent focused on the most relevant information. As findings accumulate over many iterations, you may want to summarize earlier findings rather than passing them raw.

9.2.3 Understanding iteration body output

Before we jump into the main decision block, we want to cover the output generated by each agent iteration. The iteration output captures the work that happens during each cycle of the loop. This is where the agent senses, plans, acts, and learns. In code, the iteration body is typically a single call to Runner.run() with the current state/plan as context, followed by parsing the agent’s output to update the state.

The iteration output (ResearchIteration) should be designed to ensure the agent produces structured output that the loop controller can parse. This is important because the loop controller needs to extract specific pieces of information from each iteration: what the agent found, what it wants to do next, and whether it believes the goal has been met. The following listing shows a strongly typed output model for a research iteration. This model includes a sub-object that also tracks subtopic updates.

Listing 9.3 03_iteration_output.py (iteration body)
class SubTopicUpdate(BaseModel):    #1
    """An update to a single sub-topic in the plan."""
    name: str
    status: str  # pending | in_progress | complete
    notes: str = ""

class ResearchIteration(BaseModel):    #1
    """Output from a single research iteration."""
    summary_of_findings: str    #2
    sources_used: list[str]     #2
    follow_up_questions: list[str]     #2
    goal_satisfied: bool     #2
    confidence: float     #2
    reasoning: str     #2
    plan_updates: list[SubTopicUpdate] = []       #3
    new_sub_topics: list[SubTopicUpdate] = []    #4
    strategy_notes: str = ""
#1 Using nested objects is an excellent way of requiring structure in the agent outputs.
#2 The fields will require the agent to output key metrics and status about the iteration through self-assessment, such as if the goal is satisfied with high confidence
#3 Updates that will be applied to the plan for the next iteration
#4 A set of subgoals (topics) the agent identifies that still need to be solved

Using strongly typed output here is nonnegotiable. Without it, you are left parsing free-text responses to determine loop control flow, which is fragile and error prone. The follow_up_questions and goal_satisfied fields are particularly important because they drive the next iteration. When this list is empty, or the goal is marked as satisfied, it signals to the state that there is nothing left to investigate. This triggers termination.

Strongly typed output with agents

Remember that when we use strongly typed output with the Agents SDK, we do not call out the output format in the agent instructions. The SDK handles passing the output format as part of the instructions. By allowing the SDK to manage output typing, we avoid the need to modify the agent instructions for every class change.

9.2.4 The termination gate

The termination gate is the decision point at the end of each iteration that determines whether the loop continues or exits. As we established earlier, termination conditions should always be layered. Here is an example of some priorities you may want to consider:

  • Hard limit—Maximum iteration count. This is your safety net and should always be present. Setting this limit depends on how long you want the agent to run to produce good output.
  • Budget limit—Maximum token or cost spend. Critical for production systems with cost constraints. To better control costs, reduce the number of tokens an agent consumes per iteration.
  • Goal satisfaction—The agent declares that its goal has been met. This is the ideal exit path, but it is also an internal self-assessment that could be biased. To address this bias, you could introduce another goal agent to make this decision.
  • Quality threshold—An external evaluator or the agent’s own self-evaluation exceeds the minimum confidence bar. Since this is a self-assessment, you may want to use a quality agent or a combined goal/quality agent to control it.
  • Stagnation detection—The agent’s output has not meaningfully changed for N iterations. This prevents loops that produce diminishing returns. The to_context function can help normalize outputs and track major changes.

Hard limits and budget limits are defensive and nonnegotiable. Goal satisfaction and quality thresholds indicate that the agent is doing its job well. Stagnation detection is the safety valve for cases where the agent isn’t failing but also isn’t making progress, endlessly rephrasing the same findings or running similar searches.

Stagnation is harder to detect than failure

A failing agent throws errors or returns empty results, both of which are easy to catch. A stagnating agent returns plausible-looking output that is not meaningfully different from what it produced two iterations ago. To detect this, compare the semantic overlap between consecutive iteration summaries. You can check semantic overlap by converting both sets of text to vector embeddings and then measuring cosine similarity. If the overlap exceeds a threshold (say, 85%) for two consecutive iterations, terminate the loop and return what you have. The extra iterations are not adding value.

The cost of unconstrained loops

An agentic loop without a hard termination condition is a production incident waiting to happen. Every iteration consumes tokens, incurs API costs, and adds latency. During development, it is tempting to let the agent loop until it is “satisfied,” but in production, you must always set a maximum iteration count and cost ceiling. Even if you trust the agent’s judgment on convergence, a defensive maximum protects you from edge cases where the model gets stuck in a reasoning loop or keeps searching for information that does not exist.

9.2.5 Coding the deep research loop

Now, let’s put together the full research loop. Listing 9.4 shows the complete deep research agent. It includes the loop controller, the agent definition, the MCP server setup, and the termination code. Pay attention to how state flows from one iteration to the next and how the termination conditions work together. This code covers the entire iteration loop illustrated in figure 9.4 except for the secondary agent that combines everything into a formatted output report.

Notice how the agent instructions tell the agent that it is running within a loop. They also show how to initialize the plan and state, as well as how to set the stop condition. Listing 9.4 04_deep_research_loop.py (agent init)
research_agent = Agent(
    name="Deep Research Agent",
    instructions="""    #1
You are a deep research agent.
Your goal is to thoroughly research a topic by searching for
information, reading results, and synthesizing findings.

RESEARCH PLAN:
- On your FIRST iteration (when no plan exists yet), analyze the
  research goal and create a plan by returning sub-topics in
  new_sub_topics. Each sub-topic should be a distinct aspect of
  the goal. Set status to "pending" for unstarted topics and
  "in_progress" for the one you are currently researching.
- On SUBSEQUENT iterations, update existing sub-topics via
  plan_updates (change status to "in_progress" or "complete",
  add notes summarizing what was learned). You may also add
  new sub-topics via new_sub_topics if you discover the research
  requires areas not in the original plan.
- Use strategy_notes to record high-level observations about
  your research approach or adjustments to strategy.

Each iteration, review your plan and accumulated state, identify
gaps, search for new information, and update your findings.
follow_up_questions should contain specific search queries for
the next iterations. The plan provides strategic direction while
follow_up_questions drive tactical execution.

When you believe you have sufficient information to answer
the research goal comprehensively, set goal_satisfied to true.
""",
    model="gpt-5.1",        #2
    output_type=ResearchIteration,
)

def apply_plan_updates(    #3
    plan: ResearchPlan, iteration: ResearchIteration
) -> None:
    """Apply plan changes from an iteration to the mutable plan."""
    existing = {st.name: st for st in plan.sub_topics}
    for update in iteration.plan_updates:
        if update.name in existing:
            existing[update.name].status = update.status
            if update.notes:
                existing[update.name].notes = update.notes

    for new_st in iteration.new_sub_topics:
        if new_st.name not in existing:
            plan.sub_topics.append(
                SubTopic(
                    name=new_st.name,
                    status=new_st.status,
                    notes=new_st.notes,
                )
            )

    if iteration.strategy_notes:
        plan.strategy_notes = iteration.strategy_notes
#1 The agent instructions inform the agent it is running within a loop.
#2 A model that can effectively execute the tools it needs to perform each subtopic/task
#3 Updates the plan with updates provided from the iteration body output

A lot is happening in listing 9.4, so let’s walk through the key design decisions. First, the to_context method passes only the last five findings to the agent. This is a deliberate tradeoff between context richness and context window management. In a loop that runs for 10 iterations, passing all findings would consume a significant portion of the context window. That would leave less room for the agent to think and for tool results. By truncating to the most recent findings, we keep the agent focused on the latest information while trusting that earlier findings have already been synthesized into later ones.

Next, the loop pops questions from the front of the follow_up_questions list and appends new questions to the end. This creates a breadth-first exploration pattern. If you want depth-first exploration instead (pursuing each thread fully before moving to the next), pop from the end of the list. The choice between breadth-first and depth-first exploration is a tunable parameter that should match your research use case. In effect, we are performing a tree-of-thought search here.

Listing 9.5 04_deep_research_loop.py (complete research loop)
async def run_research_loop(    #1
    goal: str, max_iterations: int = 10
) -> ResearchState:
    search_server = MCPServerStdio(
        name="Brave Search",
        params={
            "command": "npx",
            "args": ["-y", "@anthropic/brave-search-mcp"],
            "env": {"BRAVE_API_KEY": os.environ["BRAVE_API_KEY"]},
        },
    )
    async with search_server:
        agent = research_agent.clone(
            mcp_servers=[search_server]
        )
        state = ResearchState(    #2
            goal=goal,
            max_iterations=max_iterations,
            follow_up_questions=[goal],
        )

        while state.should_continue:    #3
            state.iteration_count += 1
            question = state.follow_up_questions.pop(0)
            input_context = dict(
                current_question=question,
                accumulated_state=state.to_context(),
                research_plan=state.plan.to_context(),
            )
            print(f"\n--- Iteration {state.iteration_count} ---")
            print(f"Investigating: {question}")

            result = await Runner.run(
                agent, input=str(input_context)
            )
            iteration = result.final_output

            state.findings.append(iteration.summary_of_findings)
            state.sources_consulted.extend(iteration.sources_used)
            state.follow_up_questions.extend(
                iteration.follow_up_questions
            )
            apply_plan_updates(state.plan, iteration)

            if iteration.goal_satisfied:    #4
                state.status = "complete"
                print(f"Goal satisfied (confidence: "
                      f"{iteration.confidence:.0%})")

            print(f"Found: {iteration.summary_of_findings[:100]}...")
            print(f"New questions: {len(iteration.follow_up_questions)}")
            print(f"Plan: {state.plan.progress_summary}")

        return state

async def main():    #5
    state = await run_research_loop(
        goal="What are the latest advances in solid-state batteries "
             "and which companies are leading commercialization?",
        max_iterations=8,
    )
    print(f"\n{'='*50}")
    print(f"Research complete after {state.iteration_count} iterations")
    print(f"Sources consulted: {len(state.sources_consulted)}")
    print(f"Status: {state.status}")
    print(f"Plan progress: {state.plan.progress_summary}")
    if state.plan.sub_topics:
        for st in state.plan.sub_topics:
            print(f"  [{st.status}] {st.name}")
    for i, finding in enumerate(state.findings, 1):
        print(f"\nFinding {i}: {finding[:200]}...")

asyncio.run(main())
#1 The main code that executes the full level-2 agentic loop
#2 Initializes the main state object
#3 Performs the loop until the agent’s stop condition is met or maximum iterations have been exceeded
#4 If the goal has been satisfied, prepares to exit the loop.
#5 Main loop that runs the research loop and outputs the results

Notice how the MCP server is created and connected within the run_research_loop function using an async context manager. This ensures that the server is properly shut down when the loop completes, even if an exception occurs. Never leave MCP servers running after the loop exits. They consume resources and can cause port conflicts in subsequent runs.

9.2.6 Synthesizing the final output

After the loop completes, we have a list of findings, but we don’t yet have a coherent, well-structured research report. The findings are snapshots from individual iterations and may overlap, contradict, or leave gaps. To produce a polished final output, we run a separate synthesis agent that uses the accumulated state to produce a unified report.

Listing 9.6 shows the synthesis agent and how it is called after the loop completes. This agent is deliberately separate from the research agent to maintain a clean separation of concerns: the research agent explores, and the synthesis agent compiles.

Listing 9.6 05_research_synthesis.py (synthesis agent)
class ResearchReport(BaseModel):    #1
    title: str
    executive_summary: str
    key_findings: list[str]
    sources: list[str]
    confidence_assessment: str
    gaps_and_limitations: str

synthesis_agent = Agent(    #2
    name="Research Synthesizer",
    instructions="""
You are a research synthesis agent.
Given a set of research findings, their sources, and the
research plan with sub-topics, produce a comprehensive,
well-structured research report.
Use the research plan's sub-topics as a structural guide
for organizing your report sections.
Identify themes, resolve contradictions between findings,
and note any gaps or limitations in the research.
Mark any plan sub-topics that were not fully completed
as gaps in your report.
""",
    model="gpt-5.1",    #3
    output_type=ResearchReport,
)

async def synthesize_research(state: ResearchState) 
-> ResearchReport:    #4
    synthesis_input = dict(
        goal=state.goal,
        all_findings=state.findings,
        all_sources=list(set(state.sources_consulted)),
        iterations_completed=state.iteration_count,
        final_status=state.status,
        research_plan=state.plan.to_context(),
    )

        synthesis_agent, input=str(synthesis_input)
    )

#1 Strongly typed report structure for the final output
#2 A separate synthesis agent with a focused role
#3 Selects a model that can formulate the output but not so smart that it attempts to perform additional research, which advanced reasoning models may be inclined to do
#4 Function to prepare inputs for synthesis and then call and return the structured report

Notice that in the synthesis step, we pass all findings to the synthesis agent, not just the last five. This is because the synthesis agent runs once rather than in a loop, so the context window pressure is lower. The synthesis agent also receives the final status, which indicates whether the research goal was fully met or the loop was terminated early. This status allows the agent to appropriately caveat its report.

Separation of concerns in agent loops

It is tempting to have the research agent produce a final report on its last iteration. Resist this temptation. The research agent’s job is to explore and discover. The synthesis agent’s job is to compile and structure. When you combine these responsibilities, you get agents that start optimizing for report structure during exploration, which degrades search quality. Keep them separate, and each agent can focus on what it does best.

9.2.7 When to use an agentic loop

Not every agent needs a loop. Use the agentic loop when the task has one or more of the following characteristics:

  • Iterative discovery—The agent cannot get all the information it needs in a single step. Research, analysis, and exploration tasks almost always fall into this category.
  • Progressive refinement—The output improves with each iteration. Writing, summarization, and content generation can benefit from iterative drafts.
  • Batch processing—There is a queue of items to process, and the agent works through them one at a time or in small batches.
  • Conditional branching—The agent’s next action depends on the result of the previous action. Diagnostic agents, troubleshooting flows, and decision trees use this pattern.
  • Multisource aggregation—The agent needs to combine information from multiple sources, and the relevant sources are discovered during execution rather than known in advance.

Conversely, avoid the agentic loop for tasks that require a single pass. Classification, simple question-answering, and format conversion rarely benefit from iteration. Adding a loop to these tasks only adds latency and cost without improving quality.

9.2.8 Building a repetitive task loop agent

The second major pattern for the agentic loop is repetitive task completion. Unlike research agents, which explore and discover, task agents have a well-defined work queue and process items sequentially. Think of batch-processing invoices, transforming a series of documents, running tests against multiple endpoints, or migrating records from one system to another.

Figure 9.5 shows the architecture of a repetitive task loop agent. The agent maintains a task queue, processes one item per iteration, updates the progress tracker, and continues until the queue is empty or a termination condition is met.

Figure 9.5 Workflow of a repetitive task loop agent. The agent pulls items from a task queue, processes each one using tools from MCP servers, records the result, and tracks progress until the queue is empty or a stop condition fires.

Again, the state (queue of items) and decision flow are external to the agent performing the task. Because the agent is iterating over a well-defined list, an external plan is not needed for this variation of the agent loop.

The code for the task loop agent is provided in the 07_task_loop.py file within this chapter’s source code. It demonstrates how to process a list of files using an MCP file­system and Brave Search server. This example is easy to adapt to other task lists you may need an agent to perform.

9.3 Layer 3: Multi-agent orchestration loops

With the layer-2 task and research loops established, we now turn to the layer-3 meta loop. Recall from section 9.1 that the meta loop places an agent, rather than code, in control of the decide, state, and plan elements. In the orchestration subtype, a single orchestrator agent delegates work to specialized subagents, evaluates their results, and decides whether to loop again or finalize the output.

Figure 9.6 shows the architecture of an orchestrator-controlled meta loop. The orchestrator maintains the global plan and state, delegates individual tasks to worker agents as tool calls, and evaluates whether the collective output satisfies the goal.

Figure 9.6 The diagram shows orchestrator agent loop flow. It also shows how the state and plan are accessed and managed, what decisions are made, and how tasks are delegated to worker agents.

The key difference between this and the layer-2 loop is that the orchestrator is itself an LLM-driven agent. It reasons about which subtask to pursue next, whether a worker’s output is adequate, and whether the plan needs adjustment. This makes the meta loop adaptive in ways that a hardcoded for loop cannot be.

Listing 9.8 08_orchestrator_loop.py (orchestrator meta loop)
async def run_orchestrator_loop(                              #1
    goal: str, max_iterations: int = 15
) -> ResearchState:
    search_server = MCPServerStdio(
        name="Brave Search",
        params={
            "command": "npx",
            "args": ["-y", "@anthropic/brave-search-mcp"],
            "env": {"BRAVE_API_KEY": os.environ["BRAVE_API_KEY"]},
        },
    )
    async with search_server:
        workers = {                                           #2
            "Research Worker": research_worker.clone(
                mcp_servers=[search_server]
            ),
            "Analysis Worker": analysis_worker,
        }
        state = ResearchState(
            goal=goal, max_iterations=max_iterations,
            follow_up_questions=[goal],
        )
        plan = OrchestratorPlan()
        for iteration in range(max_iterations):               #3
            orch_input = dict(
                goal=state.goal,
                current_state=state.to_context(),
                plan=str(dict(
                    sub_tasks=[
                        dict(name=st.name, status=st.status,
                             notes=st.notes)
                        for st in plan.sub_tasks],
                    strategy=plan.overall_strategy,
                    focus=plan.current_focus,
                )),
                iteration=iteration + 1,
                max_iterations=max_iterations,
            )
            decision = (await Runner.run(
                orchestrator_agent, input=str(orch_input)
            )).final_output

            if decision.is_complete or \
               decision.next_action == "finalize":            #4
                state.status = "complete"
                break

            if decision.next_action == "delegate":            #5
                worker = workers.get(decision.target_worker)
                if worker:
                    worker_result = (await Runner.run(
                        worker, input=decision.task_description
                    )).final_output
                    state.findings.append(
                        worker_result.summary_of_findings
                    )
                    state.sources_consulted.extend(
                        worker_result.sources_used
                    )
                    apply_plan_updates(
                        state.plan, worker_result
                    )

            if decision.next_action == "re_plan":             #6
                for update in decision.plan_updates:
                    existing = {st.name: st
                                for st in plan.sub_tasks}
                    if update.name in existing:
                        existing[update.name].status = \
                            update.status
                    else:
                        plan.sub_tasks.append(SubTopic(
                            name=update.name,
                            status=update.status,
                            notes=update.notes,
                        ))

            state.iteration_count = iteration + 1
        return state
#1 Main function that runs the orchestrator loop with MCP server setup
#2 Worker agents are stored in a dictionary for dynamic dispatch by the orchestrator.
#3 The orchestrator iterates, making decisions at each step about what to do next.
#4 If the orchestrator decides the goal is complete, exit the loop.
#5 When delegating, the orchestrator routes work to the appropriate worker agent.
#6 When replanning, the orchestrator updates the global plan based on what has been learned.

The orchestrator pattern is powerful because it separates strategic reasoning (which subtask to pursue, whether to replan) from tactical execution (searching and analyzing). The orchestrator never touches a search tool directly; it reasons about what needs to happen next and delegates the actual work. This mirrors how effective human managers operate: they plan, delegate, and evaluate rather than doing every task themselves.

Notice that the orchestrator can dynamically replan mid-loop. If a worker’s findings reveal that the original decomposition was incomplete, the orchestrator can add new subtasks or reprioritize existing ones. This adaptability is what makes the meta loop genuinely more capable than a static layer-2 loop for complex, multifaceted goals, especially goals that may change while the orchestrator is working through the problem.

Orchestrator overhead

Every orchestrator’s decision is an LLM call. In a 15-iteration loop, that is 15 additional calls on top of the worker calls. For straightforward tasks where the decomposition is known in advance, a layer-2 loop with hardcoded task dispatch is cheaper and faster. Reserve the orchestrator pattern for goals where the decomposition itself is uncertain or where the plan must evolve based on intermediate results.

9.4 Building collaborative agentic loops

The second subtype of the layer-3 meta loop is collaboration, where multiple agents participate as peers rather than in a delegator-worker hierarchy. In a collaboration loop, agents share state and collectively decide when the goal is met. There is no single orchestrator; instead, the agents take turns contributing to, critiquing, and refining each other’s work.

Figure 9.7 shows the architecture of a collaborative meta loop. Multiple agents share a common state object and cycle through contribution rounds. A lightweight turn manager controls whose turn it is, but the agents themselves drive the content and decide when to stop.

Figure 9.7 The component workflow for an agent-collaboration layer-3 meta-agentic loop

The collaboration pattern excels when different perspectives improve the output. A common configuration is the researcher-critic-synthesizer triad: one agent generates findings, another challenges and verifies those findings, and a third weaves the validated findings into a coherent narrative. Each agent sees the full shared state, including contributions from other agents, so each round builds on the collective work rather than on isolated effort.

Typically, in this type of agentic-loop collaboration pattern, agents follow a cycle of contributor followed by critic (grounding, QA, or another agent that critiques the work). Advanced patterns may evolve so that the agent itself selects the next agent. This could allow agents to iterate over their own work before sending it to a critic agent. Essentially, it allows a layer-2 agent loop to exist within a layer-3 collaboration meta loop.

Listing 9.9 09_collaboration_loop.py (collaboration meta loop)
class Contribution(BaseModel):
    """A single agent's contribution to the shared state."""
    agent_name: str
    content: str
    critique: str = ""
    suggestions: list[str] = []
    agrees_goal_met: bool = False
    confidence: float = 0.0

class CollaborationState(BaseModel):
    """Shared state for a collaborative agent loop."""
    goal: str
    contributions: list[Contribution] = Field(
        default_factory=list
    )
    round_number: int = 0
    max_rounds: int = 5
    consensus_threshold: float = 0.8                          #1

    @property
    def has_consensus(self) -> bool:                           #2
        if len(self.contributions) < 2:
            return False
        recent = self.contributions[-3:]
        if not recent:
            return False
        agreeing = sum(1 for c in recent if c.agrees_goal_met)
        return agreeing / len(recent) >= self.consensus_threshold

    def recent_context(self, n: int = 6) -> str:
        recent = self.contributions[-n:]
        return str([
            dict(agent=c.agent_name, content=c.content[:500],
                 critique=c.critique, agrees=c.agrees_goal_met)
            for c in recent
        ])
#1 Threshold for consensus—what fraction of recent agents must agree the goal is met
#2 Checks whether the most recent agents have reached consensus on goal satisfaction

Listing 9.11 09_collaboration_loop.py (collaboration meta loop)
async def run_collaboration_loop(                             #1
    goal: str, max_rounds: int = 5
) -> CollaborationState:
    agents = [researcher_agent, critic_agent,
              synthesizer_agent]
    search_server = MCPServerStdio(
        name="Brave Search",
        params={
            "command": "npx",
            "args": ["-y", "@anthropic/brave-search-mcp"],
            "env": {"BRAVE_API_KEY": os.environ["BRAVE_API_KEY"]},
        },
    )
    async with search_server:
        agents[0] = researcher_agent.clone(                   #2
            mcp_servers=[search_server]
        )
        state = CollaborationState(
            goal=goal, max_rounds=max_rounds
        )
        agent_index = 0
        while (state.round_number < state.max_rounds
               and not state.has_consensus):                  #3
            current_agent = agents[agent_index % len(agents)]
            collab_input = dict(
                goal=state.goal,
                your_role=current_agent.name,
                round=state.round_number + 1,
                recent_contributions=state.recent_context(),
            )
            print(f"\nRound {state.round_number + 1}, "
                  f"Agent: {current_agent.name}")
            result = await Runner.run(
                current_agent, input=str(collab_input)
            )
            contribution = result.final_output
            contribution.agent_name = current_agent.name
            state.contributions.append(contribution)
            print(f"  Content: {contribution.content[:100]}...")
            print(f"  Agrees goal met: "
                  f"{contribution.agrees_goal_met}")

            agent_index += 1
            if agent_index % len(agents) == 0:                #4
                state.round_number += 1

        return state
#1 Main function that runs the collaboration loop with round-robin agent rotation
#2 Only the researcher needs search tools. The critic and synthesizer work from existing findings.
#3 The loop continues untilconsensus is reached or maximum rounds are exhausted.
#4 A full round completes when all agents have contributed once.

The collaboration pattern produces higher-quality output than a single-agent loop for tasks that benefit from adversarial validation. The critic catches unsupported claims and factual gaps that a lone research agent might gloss over. The synthesizer resolves contradictions that the researcher and critic surface through their back-and-forth. Each round refines the collective understanding.

Collaboration vs orchestration: When to use which

Use orchestration when the goal naturally decomposes into independent subtasks that can be assigned to specialists. Use collaboration when the subtasks are interdependent and benefit from multiple perspectives. Research synthesis, document review, and strategic analysis are natural fits for collaboration. Data pipeline processing, parallel search, and batch transformations are better served by orchestration. If you are unsure, start with orchestration (it is simpler to debug) and promote collaboration only when output quality requires adversarial review.

Deciding where to use collaboration versus orchestration depends on your use case. For simple batch tasks, orchestration works well. For tasks that require more adversarial review, use collaboration.

Summary

  • The agentic loop is the core iteration engine that powers research agents, task agents, and any agent that must iterate toward a goal rather than answer in a single pass.
  • Every agentic loop rests on three pillars: a goal (what to achieve), an iteration strategy (what to do each cycle), and termination conditions (when to stop). All three must be explicit in your design.
  • State accumulators carry context between iterations. Control what the agent sees at each cycle to manage context window usage by truncating, summarizing, or compressing earlier findings as the loop progresses.
  • Strongly typed iteration output (Pydantic models) is nonnegotiable for loop agents. The loop controller needs structured data, such as follow-up questions, goal satisfaction flags, and confidence scores, to manage flow control.
  • Termination conditions should be layered: hard iteration limits (safety net), budget limits (cost control), goal satisfaction (ideal exit), quality thresholds (evaluator-­driven), and stagnation detection (diminishing returns).
  • MCP servers provide dynamic tool discovery for loop agents, allowing agents to search the web, access filesystems, and call external services without hardcoding @function_tool wrappers. Use MCPServerStdio with async context managers for clean lifecycle management.
  • Deep research loops iterate through search-read-synthesize cycles, accumulating findings and generating follow-up questions. Use a separate synthesis agent to compile findings into a polished report after the loop completes.
  • Repetitive task loops process work queues with retry logic for transient failures. Track completed, failed, and pending items explicitly, and feed previous errors back to the agent on retries.
  • Parallel iteration with asyncio.gather dramatically speeds up task loops when items are independent, but watch rate limits and ensure task independence before enabling it.
  • Adaptive iteration budgets let the agent estimate and request iteration counts based on task complexity while respecting hard ceilings set by the developer.
  • Never deploy an agentic loop without both a hard iteration limit and a cost ceiling. An unconstrained loop is a production incident waiting to happen.
